2. API-004: tienes razón, debía ser “No verificable”
La clasificación correcta es:

Existe una Capa o un Flujo candidato, pero no puede certificarse que esté asociado a la API principal.

API-004 sería No cumple si estuvieran demostradas simultáneamente estas condiciones:
La API es MCI.

¿La regla induce a confusión?
No realmente. La regla distingue expresamente:

No verificable: existe una capa o flujo candidato, pero no se puede certificar su asociación.

“Está certificada la ausencia de despliegue”.

2. Mejora propuesta para API-004
La regla actual ya contempla el caso, pero deja demasiado cerca dos ideas distintas:
Que falte una asociación.
Que la asociación no pueda certificarse.
Eso facilita interpretar incorrectamente que deploymentAssociations: [] equivale a ausencia demostrada. La mejora debe dejar explícito que:
La ausencia de evidencia positiva no es evidencia de ausencia.
Redacción propuesta
No modificaría el propósito ni la obligación de API-004. Ajustaría principalmente los apartados Evidencia mínima, No cumple y No verificable.
Evidencia mínima propuesta
Evidencia mínima: Identificación certificada de la API principal, tipo de exposición obtenido de la tercera sección o declarado por la analista, condición MCI o no MCI declarada por la analista e inventario completo de las Capas de Arquitectura, Flujos Transaccionales y asociaciones de despliegue de la página.
La declaración de la analista determina la condición MCI y, cuando corresponda, el tipo de exposición, pero no demuestra la existencia, ausencia ni asociación de una Capa de Arquitectura o un Flujo Transaccional.
Un campo deploymentAssociations ausente, vacío o sin una asociación positiva para la API principal no demuestra por sí solo que la API carezca de los elementos de despliegue exigidos. Para certificar su ausencia se requiere cobertura suficiente del inventario y de las asociaciones, sin capas o flujos candidatos pendientes de atribución.
Esta adición corrige exactamente el punto que originó el dictamen errado.
«No cumple» propuesto
No cumple: La API principal está declarada como MCI, su tipo de exposición está determinado, el inventario de las figuras de despliegue y sus asociaciones tiene cobertura completa, y se demuestra al menos una de las siguientes situaciones:
Para una API private, no existe una Capa de Arquitectura asociada, no existe un Flujo Transaccional asociado o falta alguno de los dos.
Para una API partner, no existe una Capa de Arquitectura asociada.
El elemento requerido existe, pero está certificadamente asociado a otro componente.
La asociación existente contradice inequívocamente la pertenencia a la API principal.
Solo puede utilizarse este estado cuando la ausencia o asociación incorrecta esté certificada. La ausencia, nulidad o vaciedad de deploymentAssociations no constituye por sí sola un incumplimiento certificado.
La frase clave es la última. Evita convertir una carencia de evidencia en un No cumple.
«No verificable» propuesto
No verificable: No puede certificarse cuál es la API principal; falta la declaración de su condición MCI cuando esta determina la aplicabilidad; no puede determinarse su tipo de exposición mediante la tercera sección ni mediante una declaración de la analista; el inventario o las asociaciones de despliegue no tienen cobertura suficiente; existe una Capa de Arquitectura o un Flujo Transaccional candidato cuya asociación con la API principal no puede confirmarse ni descartarse; o el campo deploymentAssociations está ausente, vacío o no contiene una asociación para la API, sin evidencia suficiente para certificar la ausencia del elemento requerido.
Si existen capas o flujos candidatos sin propietario resuelto, prevalece No verificable sobre No cumple, salvo que exista otro incumplimiento certificado e independiente.
Este párrafo cubre exactamente lo ocurrido en tu blueprint: hay capas y flujos en la página, pero no puede atribuirse uno de cada tipo a la API principal.
