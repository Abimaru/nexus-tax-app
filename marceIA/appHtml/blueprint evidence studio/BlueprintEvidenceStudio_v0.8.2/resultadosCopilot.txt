Por qué no selecciono Text como nombre
CNT-002 exige que el hijo principal tenga un nombre visible, funcional y específico. Para determinarlo debo respetar la interpretación entregada por el contrato enriquecido, especialmente:


components[].name
y su reflejo en:


inventory.serviciosHijo[].name
En este caso ambos están vacíos. El contenido de Text ya fue proyectado por Evidence Studio hacia:


"operation": "ms_key_management_spi"
Por eso tomar nuevamente ese mismo valor como name sería una inferencia propia que contradice la normalización del JSON. También eliminaría artificialmente la diferencia entre:


"name": ""
y:


"operation": "ms_key_management_spi"
La regla de precedencia indica que no debo corregir ni reinterpretar tipos, roles o propiedades por nombre, posición o conveniencia. Debo usar las propiedades como vienen diferenciadas en el contrato.

y para que es el campo operation?
BlueGuard 11.8.2
BlueGuard 11.8.2
El campo operation representa la operación funcional que ejecuta o expone un componente, no el nombre arquitectónico del componente.
En el hijo principal
Para“(sin texto: SERVICIO_HIJO)” (2kV7IvZMMpdu) aparece:


{
  "name": "",
  "architecturalType": "SERVICIO_HIJO",
  "role": "INVOCADO",
  "operation": "ms_key_management_spi"
}
Esto se interpreta así:
Campo	Significado	Valor
name	Nombre visible del componente	Vacío
architecturalType	Tipo arquitectónico	SERVICIO_HIJO
role	Papel dentro del escenario	INVOCADO
operation	Operación o capacidad funcional representada por el hijo	ms_key_management_spi
En este caso, operation sirve para indicar que el hijo principal representa o ejecuta ms_key_management_spi dentro del escenario updateInformationKey.
sharepoint

El componente se llama“Real Time Payments QR Keys Management - Commerce Keys v1.1.1” (2kV7uK_w2YrK).

Particularidad del SERVICIO_HIJO
En un bloque API o servicio, las áreas suelen proyectarse así:


Title → name
Text1 → operation
Text2 → clasificación
En el contenedor hijo aparecen:


"textAreas": [
  {
    "label": "FloatingTitle",
    "text": ""
  },
  {
    "label": "Text",
    "text": "ms_key_management_spi"
  }
]
El enriquecedor interpretó:


FloatingTitle vacío → name vacío
Text con ms_key_management_spi → operation
Por tanto, operation permite saber qué servicio o capacidad representa el hijo, aunque no exista un título visible separado para el contenedor.
sharepoint
Relación con las reglas
En CNT-002, operation ayuda a comprender qué representa el hijo, pero no reemplaza el nombre requerido.
En API-002, la operación se valida formalmente mediante la segunda sección de cada API.
En SRV-002, la operación se valida formalmente mediante la segunda sección de cada servicio.
El hijo principal queda excluido de SRV-002, porque esa regla excluye expresamente a los hijos principales de E1, E2 y E3.
En síntesis:


name      = cómo se llama el componente
operation = qué operación ejecuta o expone
En“(sin texto: SERVICIO_HIJO)” (2kV7IvZMMpdu) conocemos qué representa, ms_key_management_spi, pero el JSON enriquecido no certifica un nombre visible independiente para el contenedor.
