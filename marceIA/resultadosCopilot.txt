REQUERIMIENTO DE MEJORA DEL HTML GENERADOR DEL JSON ENRIQUECIDO
Blueprint Evidence Studio

1. OBJETIVO

Ajustar el HTML que genera el JSON enriquecido para que:

1. Conserve y exponga todas las clasificaciones declaradas en `customData` del JSON original.
2. Identifique y relacione modelos de entrada y salida con API, servicios y eventos de integración.
3. Distinga componentes principales, consumidos, externos y pertenecientes a otros dominios.
4. Identifique las actividades funcionales del flujo sin depender de que su nombre comience con un verbo en infinitivo.
5. Evalúe por separado la nomenclatura de las actividades funcionales.
6. Identifique comunicaciones bidireccionales entre actividades automatizadas y API o servicios.
7. Quede preparado para futuras clasificaciones de figuras mediante `customData.KEY`, sin requerir cambios estructurales cada vez que se añada un nuevo KEY.
8. Conserve separadas:
   - la evidencia declarada en el JSON original;
   - la clasificación inferida por el enriquecedor;
   - la evaluación normativa que posteriormente realizará el agente.

El JSON enriquecido debe permitir que el agente de validación tome decisiones sin consultar el JSON original y sin utilizar proximidad, coordenadas, colores, apariencia visual, alineación o interpretación manual del diagrama.


2. PRINCIPIO GENERAL DE TRAZABILIDAD

Toda figura del JSON original debe conservar en el JSON enriquecido:

- id;
- class;
- textos originales;
- customData completo;
- referencias a grupos;
- referencias a contenedores;
- conexiones entrantes;
- conexiones salientes;
- ruta jerárquica;
- fuente de cada dato;
- clasificaciones declaradas;
- clasificaciones inferidas;
- confianza de las inferencias;
- evidencia utilizada;
- advertencias o contradicciones.

No eliminar ni resumir los elementos de `customData`.

Ejemplo:

{
  "id": "FIGURE_ID",
  "class": "BPMNActivity",
  "texts": [
    {
      "label": "Text",
      "value": "Consultar información del cliente"
    }
  ],
  "customData": [
    {
      "key": "ACTIVIDAD_AUTOMATIZADA",
      "value": ""
    }
  ],
  "groupReferences": [],
  "containerReferences": [
    "CONTAINER_ID"
  ],
  "incomingConnectionIds": [],
  "outgoingConnectionIds": [],
  "hierarchyPath": [
    "CORE GLOBAL ACCOUNT",
    "user_ms"
  ]
}


3. SOPORTE GENÉRICO DE CUSTOMDATA.KEY

Actualmente algunos modelos tienen:

- ENTRADA;
- SALIDA.

A futuro otras figuras tendrán KEY para diferenciar, por ejemplo:

- evento de inicio;
- evento de fin;
- evento de excepción;
- modelo de entrada;
- modelo de salida;
- definición;
- política;
- excepción;
- actividad automatizada;
- actividad de sistema;
- actividad de consulta;
- otros tipos todavía no definidos.

El HTML no debe codificar únicamente ENTRADA y SALIDA.

Debe conservar cualquier KEY recibido y generar una interpretación normalizada mediante un catálogo configurable.

Añadir una sección de configuración:

{
  "semanticKeyCatalog": {
    "catalogVersion": "1.0.0",
    "mappings": [
      {
        "sourceKey": "ENTRADA",
        "normalizedRole": "inputModel",
        "category": "dataModel"
      },
      {
        "sourceKey": "SALIDA",
        "normalizedRole": "outputModel",
        "category": "dataModel"
      }
    ],
    "unmappedKeys": []
  }
}

Cuando se reciba un KEY desconocido:

1. Conservarlo sin modificar.
2. No descartarlo.
3. No inventar su significado.
4. Añadirlo a `unmappedKeys`.
5. Clasificar la figura como `declaredKeyUnmapped` si no existe una correspondencia configurada.
6. Permitir añadir posteriormente su equivalencia sin cambiar la estructura del JSON enriquecido.

Ejemplo:

{
  "declaredSemantics": {
    "source": "customData",
    "keys": [
      {
        "key": "NUEVO_KEY",
        "value": "",
        "mapped": false,
        "normalizedRole": null,
        "category": null
      }
    ],
    "hasUnmappedKeys": true
  }
}


4. SEPARACIÓN ENTRE CLASIFICACIÓN DECLARADA E INFERIDA

Cada figura debe tener dos secciones independientes:

- `declaredSemantics`: contenido procedente de `customData`;
- `inferredSemantics`: clasificación calculada por el enriquecedor.

Ejemplo:

{
  "declaredSemantics": {
    "source": "customData",
    "keys": [
      {
        "key": "ENTRADA",
        "value": "",
        "mapped": true,
        "normalizedRole": "inputModel",
        "category": "dataModel"
      }
    ]
  },
  "inferredSemantics": {
    "semanticRole": "inputModel",
    "classificationSource": "declaredCustomData",
    "classificationConfidence": "high",
    "classificationScore": 1.0,
    "classificationEvidence": [
      "customData:ENTRADA"
    ],
    "excludedRoles": [],
    "reviewRequired": false
  }
}

Si existe KEY declarado, este debe tener prioridad sobre la inferencia textual.

Si la inferencia contradice el KEY:

{
  "semanticConsistency": {
    "status": "contradictory",
    "declaredRole": "inputModel",
    "inferredRole": "processActivity",
    "reviewRequired": true
  }
}

No sobrescribir la clasificación declarada con la inferida.


5. CATÁLOGO NORMALIZADO DE ROLES SEMÁNTICOS

El JSON enriquecido debe admitir, como mínimo, los siguientes roles normalizados:

Figuras BPMN:

- startEvent;
- endEvent;
- exceptionEvent;
- intermediateEvent;
- processActivity;
- automatedActivity;
- systemActivity;
- queryActivity;
- businessRule;
- errorMessage;
- exceptionMessage;
- pendingNote;
- definition;
- policy;
- unclassified.

Modelos:

- inputModel;
- outputModel;
- dataModel;
- readModel;
- bidirectionalModel;
- unclassifiedModel.

Componentes:

- mainApi;
- mainService;
- consumedInternalApi;
- consumedInternalService;
- externalApi;
- externalService;
- domainEvent;
- otherDomainEvent;
- externalEvent;
- integrationEvent;
- unknownComponent.

Estos nombres son roles normalizados internos del JSON enriquecido.

Los KEY definitivos del JSON original todavía no están definidos. Por tanto, el HTML debe permitir configurar la equivalencia entre cada KEY futuro y estos roles normalizados.


6. CLASIFICACIÓN DE COMPONENTES

Crear una colección `componentSemantics` para todas las API, servicios y eventos de integración candidatos.

Ejemplo:

{
  "componentSemantics": [
    {
      "id": "COMPONENT_ID",
      "name": "Virtual Account Opening - Virtual Account v2.1.0",
      "operation": "initiateVirtualAccount",
      "technicalType": "api",
      "normativeRole": "mainApi",
      "domainRelation": "modeledDomain",
      "classificationSource": "structuralRules",
      "classificationConfidence": "high",
      "classificationScore": 0.95,
      "classificationEvidence": [
        "locatedInIntegration",
        "connectedToMainFlow",
        "operationMatchesPage"
      ],
      "reviewRequired": false
    }
  ]
}

Valores de `technicalType`:

- api;
- service;
- integrationEvent;
- auxiliaryExternalSystem;
- unknown.

Valores de `normativeRole`:

- mainApi;
- mainService;
- consumedInternalApi;
- consumedInternalService;
- externalApi;
- externalService;
- domainEvent;
- otherDomainEvent;
- externalEvent;
- unknown.

Valores de `domainRelation`:

- modeledDomain;
- otherBankDomain;
- externalDomain;
- unknown.

El contenedor hijo del flujo, por ejemplo `user_ms`, no debe quedar obligado a tener modelos de entrada y salida por el solo hecho de ser el contenedor hijo.

Solo una API o un servicio identificado como componente principal debe tener la obligación de modelos de entrada y salida.


7. ASOCIACIÓN DE MODELOS DE ENTRADA Y SALIDA

Mantener la colección `modelAssociations`, pero ampliarla para procesar:

- grupos directos;
- grupos anidados;
- referencias semánticas explícitas;
- customData;
- futuras relaciones declaradas;
- modelos asociados a API;
- modelos asociados a servicios;
- modelos asociados a eventos de integración.

Ejemplo:

{
  "modelAssociations": [
    {
      "componentId": "COMPONENT_ID",
      "componentType": "api",
      "normativeRole": "mainApi",
      "domainRelation": "modeledDomain",
      "componentName": "Virtual Account Opening - Virtual Account v2.1.0",
      "operation": "initiateVirtualAccount",
      "associationPath": {
        "directGroupId": "GROUP_ID",
        "outerGroupId": null,
        "nestedGroupIds": []
      },
      "inputModels": [
        {
          "id": "INPUT_MODEL_ID",
          "name": "AccountOpeningRequest",
          "direction": "input",
          "directionSource": "customData:ENTRADA",
          "associationSource": "sharedGroup"
        }
      ],
      "outputModels": [
        {
          "id": "OUTPUT_MODEL_ID",
          "name": "AccountRequestAcknowledgement",
          "direction": "output",
          "directionSource": "customData:SALIDA",
          "associationSource": "sharedGroup"
        }
      ],
      "associationEvidence": [
        "sharedGroup:GROUP_ID",
        "customData:ENTRADA",
        "customData:SALIDA"
      ],
      "associationStatus": "confirmed",
      "classificationConfidence": "high",
      "reviewRequired": false
    }
  ]
}


8. ASOCIACIÓN MEDIANTE GRUPOS ANIDADOS

El HTML debe poder asociar modelos cuando:

1. Un grupo exterior contiene una única API, servicio o evento candidato.
2. Ese grupo exterior contiene un grupo interior.
3. El grupo interior contiene modelos de entrada y salida.
4. Los modelos tienen dirección declarada en `customData`.
5. No existen otros componentes candidatos que generen ambigüedad.

Ejemplo:

{
  "associationPath": {
    "directGroupId": null,
    "outerGroupId": "OUTER_GROUP_ID",
    "nestedGroupIds": [
      "INNER_GROUP_ID"
    ],
    "depth": 1
  },
  "associationStatus": "confirmed",
  "associationMethod": "nestedGroupAndCustomData"
}

Esta mejora debe permitir generar asociaciones normalizadas para componentes como:

- Customer Contact Information;
- Customer Personal Data.

No asociar modelos mediante grupos anidados si el grupo exterior contiene más de un componente candidato y no existe una referencia que permita determinar a cuál pertenece cada modelo.


9. SEPARACIÓN ENTRE MODELO, DIRECCIÓN Y ASOCIACIÓN

Para cada figura candidata a modelo, registrar por separado:

1. Si es un modelo de datos.
2. Si es de entrada o salida.
3. A qué componente está asociado.

Ejemplo:

{
  "id": "MODEL_ID",
  "semanticRole": "dataModel",
  "modelDirection": "unknown",
  "associatedComponentIds": [],
  "modelAssessment": {
    "isDataModel": {
      "status": "confirmed",
      "source": "structuredContent",
      "confidence": "medium"
    },
    "direction": {
      "status": "notVerified",
      "source": "missingCustomData",
      "confidence": "low"
    },
    "association": {
      "status": "notVerified",
      "source": "noGroupOrReference",
      "confidence": "low"
    }
  }
}

Valores de `modelDirection`:

- input;
- output;
- bidirectional;
- unknown.

No inferir dirección solamente por:

- Request;
- Response;
- Acknowledgement;
- Input;
- Output;
- orden dentro de un grupo;
- lista de campos;
- proximidad;
- coordenadas;
- posición;
- ubicación general en INTEGRACIÓN;
- ubicación general en SISTEMAS EXTERNOS.


10. ESTADO DE LAS ASOCIACIONES

Normalizar `associationStatus`:

- confirmed;
- partial;
- ambiguous;
- notVerified;
- contradictory.

Añadir:

{
  "requiredDirections": [
    "input",
    "output"
  ],
  "confirmedDirections": [
    "output"
  ],
  "missingDirections": [
    "input"
  ],
  "associationStatus": "partial",
  "absenceAssessment": {
    "input": "notFoundInAvailableEvidence",
    "output": "confirmed"
  }
}

Valores de ausencia:

- confirmed;
- notFoundInAvailableEvidence;
- confirmedAbsent;
- notApplicable;
- unknown.

No interpretar `notFoundInAvailableEvidence` como incumplimiento automático.


11. OBLIGATORIEDAD DE MODELOS

Añadir a cada componente:

{
  "modelRequirement": {
    "applies": true,
    "reason": "mainApi",
    "requiredInput": true,
    "requiredOutput": true,
    "responseMode": "requestResponse",
    "domainRelation": "modeledDomain"
  }
}

Aplicar estos criterios:

A. API principal:

- modelo de entrada obligatorio;
- modelo de salida obligatorio.

B. Servicio principal:

- modelo de entrada obligatorio;
- modelo de salida obligatorio.

C. Contenedor hijo:

- no requiere modelos por ser contenedor hijo;
- no evaluar `user_ms` como incumplimiento por carecer de modelos;
- solo requerir modelos si además existe un componente de servicio marcado expresamente como principal.

D. Eventos propios del dominio con respuesta:

- modelo de entrada obligatorio;
- modelo de salida obligatorio.

E. Eventos propios del dominio sin respuesta:

- modelo de entrada obligatorio;
- modelo de salida opcional.

F. API o servicio consumido:

- registrar los modelos cuando existan;
- no generar incumplimiento si no existen;
- su ausencia no es obligatoria para la regla de modelos.

G. API, servicio o evento externo:

- registrar los modelos cuando existan;
- no generar incumplimiento si no existen.

H. API, servicio o evento de otro dominio bancario:

- registrar los modelos cuando existan;
- no generar incumplimiento si no existen.

I. Componente cuyo dominio o rol sea desconocido:

- no concluir incumplimiento;
- indicar que la obligatoriedad no es verificable cuando la clasificación pueda modificar el resultado.


12. EVENTOS CON Y SIN RESPUESTA

Para eventos de integración, añadir:

{
  "eventSemantics": {
    "eventType": "command",
    "responseMode": "withResponse",
    "responseModeSource": "topicStructure",
    "inputRequired": true,
    "outputRequired": true,
    "classificationConfidence": "high",
    "reviewRequired": false
  }
}

Valores de `eventType`:

- query;
- command;
- event;
- unknown.

Valores de `responseMode`:

- withResponse;
- withoutResponse;
- unknown.

Criterios iniciales:

- Query: withResponse.
- Command con tópico de petición y tópico de respuesta: withResponse.
- Command con un único tópico operativo: withoutResponse.
- Event: withoutResponse.
- Si no puede determinarse el tipo o los tópicos: unknown.


13. IDENTIFICACIÓN DE ACTIVIDADES FUNCIONALES

Crear o mantener una colección `activitySemantics`.

La clasificación como actividad funcional no debe depender obligatoriamente de que el texto comience con un verbo en infinitivo.

Esto es necesario porque la regla normativa posterior comprobará precisamente la nomenclatura. Una actividad mal nombrada debe seguir siendo identificada como actividad funcional para que pueda ser marcada como incumplimiento.

Ejemplo:

{
  "activitySemantics": [
    {
      "id": "ACTIVITY_ID",
      "name": "Consulta de información del cliente",
      "semanticRole": "processActivity",
      "activityType": "unknown",
      "classificationSource": "flowAndSemanticRules",
      "classificationConfidence": "high",
      "classificationScore": 0.91,
      "classificationEvidence": [
        "class:BPMNActivity",
        "insideMainChild",
        "participatesInProcessFlow",
        "hasIncomingConnection",
        "hasOutgoingConnection",
        "notStructuredContent",
        "notInputOrOutputModel",
        "notBusinessRule",
        "notErrorMessage"
      ],
      "excludedRoles": [
        "inputModel",
        "outputModel",
        "dataModel",
        "businessRule",
        "errorMessage",
        "definition",
        "policy",
        "pendingNote"
      ],
      "reviewRequired": false
    }
  ]
}


14. CRITERIOS PARA IDENTIFICAR UNA ACTIVIDAD FUNCIONAL

Utilizar una combinación de señales.

Señales estructurales:

- class = BPMNActivity;
- pertenece al contenedor hijo principal;
- pertenece al flujo principal;
- tiene texto no vacío;
- participa en el flujo;
- tiene al menos una conexión entrante o saliente;
- está conectada con eventos BPMN, compuertas, otras actividades, API, servicios, eventos de integración o auxiliares;
- no pertenece a la leyenda o notación.

Señales semánticas:

- representa una acción ejecutable;
- tiene objeto, propósito o resultado funcional;
- no enumera campos;
- no tiene customData ENTRADA o SALIDA;
- no es una regla declarativa;
- no es una política;
- no es un mensaje de error;
- no es una excepción textual;
- no es una definición;
- no es una pregunta;
- no es una nota pendiente.

No utilizar `startsWithInfinitiveVerb` como requisito excluyente para determinar `processActivity`.


15. CLASIFICACIÓN FUTURA DEL TIPO DE ACTIVIDAD

Preparar `activityType` para recibir la clasificación futura procedente de `customData.KEY`.

Valores iniciales:

- automated;
- system;
- query;
- manual;
- unknown.

Mientras no exista un KEY declarado:

- se puede inferir el tipo;
- la inferencia debe quedar registrada como inferida;
- no debe presentarse como evidencia declarada;
- debe incluir confianza y evidencia.

Ejemplo futuro:

{
  "declaredSemantics": {
    "keys": [
      {
        "key": "ACTIVIDAD_AUTOMATIZADA",
        "mapped": true,
        "normalizedRole": "automatedActivity",
        "category": "activity"
      }
    ]
  },
  "activityType": "automated",
  "activityTypeSource": "customData",
  "activityTypeConfidence": "high"
}


16. DISTINCIÓN ENTRE ACTIVIDAD AUTOMATIZADA, DE CONSULTA Y DE SISTEMA

No clasificar una actividad por el verbo utilizado en su nombre.

En particular:

- una actividad automatizada puede comenzar con “Consultar”;
- una actividad automatizada puede comenzar con “Validar”;
- una actividad de consulta no se determina por contener la palabra “Consultar”;
- el verbo no demuestra el tipo de actividad.

La clasificación debe depender principalmente del componente con el que se comunica.

A. Actividad automatizada:

Una actividad puede inferirse como automatizada cuando:

- tiene comunicación bidireccional con una API o servicio; o
- tiene comunicación bidireccional con un auxiliar de Sistema Externo que contiene inequívocamente una API o servicio; o
- tiene un KEY futuro que la declare como automatizada.

B. Actividad de consulta:

Una actividad puede clasificarse como de consulta únicamente cuando:

- existe KEY que la declare como tal; o
- existe una inferencia estructural suficientemente sustentada;
- se comunica con componentes que no son API, servicios ni eventos de integración;
- no tiene comunicación bidireccional con API o servicios.

No clasificarla como consulta únicamente porque el texto comience con “Consultar”.

C. Actividad de sistema:

Una actividad puede clasificarse como de sistema únicamente cuando:

- existe KEY que la declare como tal; o
- existe una inferencia estructural suficientemente sustentada;
- se comunica con componentes internos que no son API, servicios ni eventos de integración;
- no tiene comunicación bidireccional con API o servicios.

Cuando no pueda distinguirse entre actividad de consulta y actividad de sistema:

- usar `activityType: unknown`;
- registrar las señales encontradas;
- utilizar `reviewRequired: true`;
- no inventar la clasificación.


17. COMUNICACIÓN BIDIRECCIONAL

Crear una colección `interactionSemantics`.

Ejemplo directo:

{
  "interactionSemantics": [
    {
      "activityId": "ACTIVITY_ID",
      "targetId": "API_ID",
      "targetTechnicalType": "api",
      "targetNormativeRole": "consumedInternalApi",
      "interactionPath": "direct",
      "outboundConnectionIds": [
        "CONNECTION_1"
      ],
      "inboundConnectionIds": [
        "CONNECTION_2"
      ],
      "isBidirectional": true,
      "interactionStatus": "confirmed",
      "classificationEvidence": [
        "activityToComponentConnection",
        "componentToActivityConnection"
      ],
      "reviewRequired": false
    }
  ]
}

La bidireccionalidad requiere dos objetos de conexión JSON distintos:

- actividad hacia API o servicio;
- API o servicio hacia actividad.

No inferir bidireccionalidad por una única conexión, proximidad o apariencia visual.


18. COMUNICACIÓN MEDIANTE SISTEMA EXTERNO AUXILIAR

Cuando una API o servicio esté encapsulado en un auxiliar de Sistema Externo, permitir:

- actividad hacia auxiliar;
- auxiliar hacia actividad.

Ejemplo:

{
  "activityId": "ACTIVITY_ID",
  "targetId": "AUXILIARY_ID",
  "targetTechnicalType": "auxiliaryExternalSystem",
  "interactionPath": "viaAuxiliary",
  "containedComponentIds": [
    "API_ID"
  ],
  "containedComponentTypes": [
    "api"
  ],
  "outboundConnectionIds": [
    "CONNECTION_1"
  ],
  "inboundConnectionIds": [
    "CONNECTION_2"
  ],
  "isBidirectional": true,
  "interactionStatus": "confirmed",
  "representsApiOrServiceInteraction": true
}

Solo afirmar que el auxiliar representa la comunicación con una API o servicio cuando la contención esté demostrada.

Una conexión con un auxiliar no demuestra por sí sola que una API, servicio o evento pertenece a ese auxiliar.


19. TRATAMIENTO DE EVENTOS EN LAS INTERACCIONES

Las actividades funcionales no deben tener comunicación directa con eventos de integración.

Si existe una conexión directa confirmada entre una actividad y un evento de integración:

{
  "interactionStatus": "invalidActivityToIntegrationEvent",
  "isBidirectional": false,
  "reviewRequired": false
}

Los eventos de integración se deben relacionar mediante la notación BPMN o el mecanismo normativo definido para ellos, no mediante la misma regla de comunicación de actividades automatizadas con API o servicios.


20. AUXILIARES QUE CONTIENEN EVENTOS

Cuando una actividad esté conectada con un auxiliar de Sistema Externo:

A. Si el auxiliar contiene inequívocamente una API o servicio:

- evaluar bidireccionalidad;
- la interacción puede corresponder a una actividad automatizada.

B. Si el auxiliar contiene únicamente eventos de integración confirmados:

- no tratar la interacción como comunicación válida de una actividad automatizada con API o servicio;
- registrar la inconsistencia.

C. Si el auxiliar contiene API o servicios y eventos, pero no puede asociarse la conexión a un componente concreto:

- `interactionStatus: ambiguous`;
- `reviewRequired: true`.

D. Si no puede determinarse qué contiene el auxiliar:

- `interactionStatus: notVerified`;
- no concluir cumplimiento ni incumplimiento;
- conservar la causa de la incertidumbre.

Ejemplo:

{
  "activityId": "ACTIVITY_ID",
  "targetId": "AUXILIARY_ID",
  "targetTechnicalType": "auxiliaryExternalSystem",
  "containedComponentTypes": [
    "unknown"
  ],
  "interactionStatus": "notVerified",
  "ambiguityReason": "Auxiliary content type is not semantically classified",
  "reviewRequired": true
}


21. EVALUACIÓN DE NOMENCLATURA DE ACTIVIDADES

Añadir una evaluación independiente:

{
  "namingAssessment": {
    "text": "Consultar datos de contacto del cliente",
    "startsWithInfinitiveVerb": true,
    "detectedVerb": "Consultar",
    "verbForm": "infinitive",

    "assessmentEvidence": [
      "initialVerb:Consultar",
      "verbForm:infinitive",
      "functionalObjectPresent"
    ],
    "recommendedName": null
  }
}

Valores de `assessmentStatus`:

- valid;
- invalid;
- notVerified;
- notApplicable.

Ejemplo de actividad funcional con nombre incorrecto:

{
  "name": "Validación de identidad del cliente",
  "semanticRole": "processActivity",
  "namingAssessment": {
    "startsWithInfinitiveVerb": false,
    "detectedVerb": null,

    "recommendedName": "Validar la identidad del cliente"
  }
}

La actividad debe permanecer dentro de la población evaluable aunque no comience con infinitivo.


22. NIVELES DE CONFIANZA

Usar:

- high;
- medium;
- low.

High:

- existe evidencia declarada; o
- existe evidencia estructural y semántica suficiente;
- no existen contradicciones;
- `reviewRequired: false`.

Medium:

- existe evidencia favorable;
- falta una señal relevante;
- la clasificación puede necesitar revisión.

Low:

- texto vacío;
- figura aislada;
- clasificación basada en una señal débil;
- evidencia insuficiente.

Las clasificaciones de confianza baja no deben utilizarse automáticamente para producir incumplimientos.


23. ADVERTENCIAS SEMÁNTICAS

Añadir `semanticWarnings` para registrar:

- KEY sin equivalencia;
- contradicción entre KEY e inferencia;
- modelo sin dirección;
- modelo sin componente asociado;
- grupo con varios componentes candidatos;
- actividad sin tipo;
- auxiliar con contenido desconocido;
- conexión con extremos sin clasificar;
- posible actividad conectada directamente a evento;
- clasificación de confianza media o baja;
- ausencia no confirmada.

}

26. CRITERIOS DE ACEPTACIÓN PARA EL BLUEPRINT ACTUAL

Modelos:

1. Debe conservar los KEY ENTRADA y SALIDA.
2. Debe identificar los modelos como inputModel y outputModel.
3. La API principal `Virtual Account Opening - Virtual Account v2.1.0 / initiateVirtualAccount` debe tener entrada y salida confirmadas.
4. `Customer Contact Information / contactByIdentification` debe tener entrada y salida asociadas mediante grupo anidado.
5. `Customer Personal Data / retrieve-detail-information` debe tener entrada y salida asociadas mediante grupo anidado.
6. `Fraud Evaluation / Transactional Risk Assessment` no debe recibir una asociación confirmada mientras no exista evidencia de dirección y asociación de sus modelos.
7. `Accounts / GET/accounts/{id}` debe permanecer como asociación parcial mientras solo tenga modelo de salida confirmado.
8. Las API externas `Users` deben conservar sus modelos asociados.
9. `user_ms` no debe marcarse como incumplimiento por no tener modelos.
10. Las API y servicios consumidos, externos o de otros dominios pueden tener modelos asociados, pero su ausencia no es obligatoria.
11. Cada componente debe tener `technicalType`, `normativeRole` y `domainRelation`.
12. Cada asociación debe distinguir existencia, dirección, asociación y obligatoriedad.

Actividades:

1. Deben identificarse las 12 actividades funcionales actuales.
2. La identificación no debe depender obligatoriamente de que comiencen con infinitivo.
3. Las 12 deben quedar relacionadas con `CORE GLOBAL ACCOUNT > user_ms`.
4. Deben registrarse sus conexiones entrantes y salientes.
5. Deben excluirse modelos, reglas, mensajes, políticas, definiciones, preguntas, pendientes y figuras vacías.
6. La evaluación del infinitivo debe quedar en `namingAssessment`.
7. Si en otro blueprint una actividad funcional no comienza con infinitivo, debe seguir siendo identificada y obtener `assessmentStatus: invalid`.
8. Una actividad no debe clasificarse como consulta por contener el verbo “Consultar”.
9. Una actividad no debe clasificarse como automatizada únicamente por contener “Consultar” o “Validar”.
10. La actividad automatizada debe identificarse por KEY declarado o por comunicación bidireccional confirmada con API o servicio.
11. Las actividades de consulta y sistema no deben requerir comunicación bidireccional con API o servicios.
12. Si no puede distinguirse entre actividad de consulta y sistema, debe usarse `activityType: unknown`.
13. No se debe aceptar conexión directa entre actividad y evento de integración como interacción válida de actividad automatizada.
14. Si un auxiliar encapsula componentes no clasificados, el resultado debe quedar `notVerified`.
15. Todos los futuros KEY deben conservarse aunque todavía no estén mapeados.


27. PRINCIPIOS QUE NO DEBEN CAMBIAR

El HTML no debe:

- inferir relaciones por proximidad;
- inferir relaciones por coordenadas;
- inferir relaciones por alineación;
- inferir relaciones por color;
- inferir relaciones por iconografía no certificada;
- inferir pertenencia a un auxiliar por una conexión;
- inferir dirección de modelos por nombres;
- inferir tipo de actividad por el verbo;
- convertir falta de evidencia en ausencia confirmada;
- sobrescribir los KEY del JSON original;
- mezclar evidencia declarada con inferencia;
- presentar una inferencia como dato declarado.

El JSON enriquecido debe ser autocontenido, trazable y compatible con los KEY actuales y futuros.
